# Offline scouting sign-in

HazeHub uses the per-account alternative, not a team-wide password-verifier roster. Each personal scouter must sign in online with an established password on each device they intend to use. **Only one account is prepared per browser profile.** Preparing another account atomically replaces previous grants and local offline sessions, but preserves scouting queues and drafts. This prevents a shared browser from accumulating the team's encrypted password verifiers. A never-provisioned account cannot sign in offline. Initial password setup remains online. Administrative, strategy, and shared picklist credentials are not provisioned.

## Provisioning and storage

After online login, `POST /api/auth/offline-provision` requires both the authenticated account and fresh proof of that same account's password. It returns only versioned identity metadata (account ID, S-number, display name, issued time, expiry). It never returns password hashes, salts from the server password database, or team credentials.

The browser derives an AES-256-GCM key with PBKDF2-HMAC-SHA256, a fresh 128-bit salt, and 600,000 iterations. It encrypts the identity grant, then encrypts that envelope with a device-local, non-exportable WebCrypto AES-GCM key. Both layers bind the schema version, account identifier and expiration as authenticated additional data. Independent random 96-bit IVs are generated for both layers. The password and derived key are not persisted. There is no server token inside the offline record.

Dexie schema version 6 adds `offlineCredentials` to the existing IndexedDB database. It holds only separately encrypted account grants, the non-exportable device CryptoKey handle, and attempt/expiry metadata. No complete team credential roster is downloaded. Online bearer tokens now live in memory rather than localStorage. An HttpOnly, SameSite cookie restores online sessions through `/api/auth/me` only; all mutations still require explicit bearer authorization. Auth responses are no longer stored in the response cache, and legacy cached auth responses and localStorage sessions are removed at startup. Nonsecret sessionStorage state prevents automatic cookie restoration after offline unlocking or signing out until a fresh password login succeeds.

## Unlock and synchronization

Offline provisioning lasts at most 24 hours. An unlock grants a scouting session lasting at most four hours, bounded by provisioning expiry. An AES-GCM encrypted local session record and a tab-local locator allow reloads and offline page navigation within that window; no server token is issued or stored. Restoring the session requires the device key and a still-valid account grant. Signing out deletes the local session record. Five failed attempts remove the account grant; exponentially increasing delays and Web Locks serialize attempts across tabs. Detected clock rollback locks the record. Expired or unsupported records are removed on use.

Offline sessions have no server bearer token and no administrative role. Server mutations are blocked. Scouting and pit submissions retain their existing local-first queues. Reconnection does not authorize uploads: the scouter must sign in online again. Queue flushing revalidates `/api/auth/me` without a cached fallback. The server checks current roster membership, role and a credential revision bound to the current password hash. Resetting/replacing a password invalidates existing tokens, including after a replacement password is established. Online rejection removes that account's local offline grant. A valid online login refreshes provisioning and resumes parked submissions belonging to that account.

Account → **Remove offline sign-ins from this device** deletes all offline grants and the device key. It preserves scouting queues and drafts. Account switching partitions queued scouting and pit reports by owner.

## Threat model and limitations

This is browser-local protection, not hardware attestation. Non-exportability prevents application code from exporting the device key's raw bytes; it does not guarantee that a complete browser/OS profile cannot be copied. Same-origin malicious code, developer tools, a compromised browser, or an attacker controlling the unlocked device can bypass client-side attempt counters and invoke stored keys. Protect devices with an OS screen lock and disk encryption. Stronger resistance to device theft requires a managed native/hardware-backed authenticator design; the app does not claim to provide that guarantee.

A disconnected device cannot learn about a server-side revocation immediately. Its last authorization expires within 24 hours, and its current unlock within four hours. Reconnection enforces revocation before uploading. Resetting the lost account's password stops further server access; it cannot remotely erase a disconnected device. Device reset removes logical access but cannot promise forensic erasure from SSD/browser backups.

Browser storage cleanup/private browsing can remove provisioning and local scouting. Persistent storage is requested by the existing app, but the browser/OS can still delete it. HTTPS (or localhost), IndexedDB, WebCrypto, and Web Locks are required for offline sign-in. Static app and event-data preparation remain necessary for offline navigation and scouting. Same-origin hosting is preferred. HTTPS deployments with a separate frontend use Secure/SameSite=None cookies; browsers that block third-party cookies may require online sign-in again after a reload. Local development should use the same hostname for frontend and backend (for example, both `localhost`, rather than mixing `localhost` and `127.0.0.1`).
